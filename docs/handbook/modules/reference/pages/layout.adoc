= Layout Engines
:description: How kUML places nodes and routes edges. ELK, kuml.grid, DSL hints.

The layout step computes positions for every diagram element. kUML ships two engines and
lets third parties register more through a ServiceLoader SPI.

== Two built-in engines

[cols="1,3"]
|===
| Engine | Character

| `elk.layered`
| https://eclipse.dev/elk/[Eclipse Layout Kernel] Sugiyama-based layered layout. Default
  for class, component, deployment, and most C4 diagrams. Handles arbitrary graphs well,
  produces aesthetically reasonable output without user input.

| `kuml.grid`
| Pure-Kotlin grid engine, GraalVM-native-image-compatible. Deterministic, hint-driven —
  you place elements on a coarse grid; the engine respects your placement. Best when you
  want predictable, hand-tuned layouts.
|===

The engine is selected per render via `LayoutEngineRegistry.pickFor(diagramKind, preferred)`:

. If `preferred` is set (CLI flag, config, or DSL hint), use it — no capability check.
. Otherwise, the first registered engine whose capabilities include the diagram type.
. Otherwise, the first engine that supports `DiagramKind.Generic`.
. Otherwise, `null` (registry empty).

Override per render:

[source,bash]
----
kuml render diagram.kuml.kts --engine kuml.grid
----

=== Spacing between components

Since 0.56.0 the layered engine spaces the components of every diagram 50 % further apart than before, so that longer
labels fit. A single constant, `LAYOUT_SPACING_SCALE` (1.5) in `kuml-layout-api`, scales the node, layer, edge-to-node and
edge-to-edge spacing; it applies to the final value, so spacing that a diagram sets itself (for example state machines,
ERM and sequence diagrams) scales alike. Group padding, box sizes and font sizes are unchanged.

State machines add one more rule (Nacharbeit 40): the layer gap is at least as wide as the widest transition label along the
flow direction (its width for `direction = Right` / `Left`, its height for `Down` / `Up`) plus 8 px on each side. The label
size comes from the same wrap (`labelMaxWidth`, default 220 px) and character estimate (7.2 px) that draw the label. The gap
is a property of the whole diagram: every layer gap widens, not only the one with the long label.

Not affected, because they use their own fixed geometry: SysML 2 activity swimlanes, Service Blueprint, the row height of
sequence diagrams, the `kuml.grid` engine and the LaTeX/TikZ output of BPMN.

== DSL hints — taking control

For predictable layouts, place a `layout { ... }` block on any element. The hints
materialize into `kuml.layout.*` metadata, the bridge reads them into the engine's
`NodeHints`, and the engine respects them (if capable).

[source,kotlin]
----
classDiagram(name = "Domain") {
    val customer = classOf("Customer") {
        layout {
            col = 0; row = 0
        }
    }

    val order = classOf("Order") {
        layout {
            col = 1; row = 0
            colSpan = 2
        }
    }

    val item = classOf("OrderItem") {
        layout {
            below(order)
            sameColAs(order)
        }
    }
}
----

Hint vocabulary:

[cols="1,3"]
|===
| Hint | Effect

| `col = N`
| Pin to column N (0-based).

| `row = N`
| Pin to row N (0-based).

| `colSpan = N`
| Element spans N columns.

| `rowSpan = N`
| Element spans N rows.

| `pinned = true`
| Engine must not move this element from its current slot.

| `above(other)`
| Place above the referenced element.

| `below(other)`
| Place below the referenced element.

| `leftOf(other)`
| Place to the left of the referenced element.

| `rightOf(other)`
| Place to the right of the referenced element.

| `sameRowAs(other)`
| Same row as the referenced element.

| `sameColAs(other)`
| Same column as the referenced element.
|===

References take either a typed val (preferred — IDE-checked) or a String ID:

[source,kotlin]
----
val order = classOf("Order")
classOf("Item") { layout { below(order) } }       // Typed reference
classOf("Item") { layout { below("Order") } }      // String — looser, also works
----

== Diagram `layout { }` block

Since the PAL 2B wave, UML diagrams (class, use case, object, package, component, composite structure,
deployment, state, activity, sequence, communication, timing, interaction overview, profile) and SysML 2
diagrams share one `layout { }` block (type `LayoutSpec`). Do not confuse it with the *element-level*
`layout { col = 2 }` of a single class; inside `classOf { }` that one applies. In UML scripts the element-level
block needs `import dev.kuml.core.dsl.layout.layout`.

[source,kotlin]
----
classDiagram(name = "Zoo") {
    // ... 11 subclasses ...
    layout {
        wrapColumns = 3
        aspectRatio = 1.6   // soft target width / height
        maxWidth = 1800     // hard upper bound in px; wins over aspectRatio
        sameLayer("Cat", "Dog")   // element handles or id strings
    }
}
----

* Id strings are accepted everywhere (`sameLayer("A::b", "A::c")`); an empty `sameLayer()` is ignored.
* `maxWidth` (200..20000) and `aspectRatio` (0.1..10) re-wrap over-wide layers; at most two layout runs.
  In state machines and block definition diagrams, an explicit `aspectRatio` or `maxWidth` without a `direction` may additionally rotate the flow direction by a quarter turn (one more run) when that lands closer to the target; an explicit `direction` is never overridden, and `KUML-LAYOUT-W003` reports the real ratio, measured on the final image (including the renderer padding) and, when a `direction` is set, with a hint that removing it allows the flow to rotate.
  In block definition diagrams with an explicit `aspectRatio`, the measurement also includes the edge-label overhang the renderer adds, so the reported ratio equals the ratio of the drawn SVG. Without an explicit `aspectRatio` the report is unchanged.
  In activity diagrams, swimlane columns and note columns are added after the layout run, so `KUML-LAYOUT-W003` is measured on the final image (width / height of the drawn diagram) and, when notes are present, says that note columns beside the swimlanes widen the diagram.
  In SysML 2 use case diagrams with an explicit `aspectRatio`, `KUML-LAYOUT-W003` is measured on the final image (renderer padding and label overhang included) and in both directions; an explicit `wrapColumns` keeps precedence over the `aspectRatio` and the message says so. Without an explicit `aspectRatio` the report is unchanged.
* `labelMaxWidth` (120..400 px, default 220) is the wrap width of transition labels. It acts on SysML 2 state machines only; every other diagram kind reports `KUML-LAYOUT-W001`, a value outside 120..400 is `KUML-LAYOUT-E001` (the value is ignored).
  A picture between 1:2.5 and 2.5:1 is never changed implicitly; outside it the layout is wrapped
  automatically (`LayoutHints.autoAspect`).
* Options a diagram kind does not honour (sequence, timing) report `KUML-LAYOUT-W001`; an unreachable
  `maxWidth` is `KUML-LAYOUT-W002`, an unreachable `aspectRatio` `KUML-LAYOUT-W003`, out-of-range values
  `KUML-LAYOUT-E001` (the value is ignored).
* Availability: the block is evaluated by `kuml render` and `kuml validate` (CLI), by kUML Desktop (render and
  validate) and by the vault tests. Web, MCP, Asciidoc, Markdown and Gradle ignore it, so the same script can
  render differently there.
* Unknown ids, more than 32 `sameLayer` groups or 64 ids per group, and ids in both `first` and `last`
  are reported (`KUML-LAYOUT-W004`, `KUML-LAYOUT-E001`, `KUML-LAYOUT-W001`).
* A `first(x)` pin on a node with incoming edges, or a `last(x)` pin on a node with outgoing edges, reports
  `KUML-LAYOUT-W008` (a warning) in `kuml validate` and `kuml render`. The pin is still applied and the diagram is
  still drawn, but the engine then draws the edge or edges against the flow direction. Remove the pin or the edge to
  clear the warning. Self-loops and edges to elements that are not nodes of the diagram are not counted.
* C4 and ERM diagrams take the block as well (`layout { }` in the diagram builder). Service Blueprint accepts it,
  but its grid ignores every option and reports `KUML-LAYOUT-W001` (see xref:blueprint.adoc[Service Blueprint]). BPMN diagram blocks are not available yet.

=== Which option acts where

Layered (ELK) pipelines honour all options: UML (except sequence and timing), SysML 2 (except sequence; this includes
package diagrams, wave 2I-a), C4, ERM
and BPMN process and collaboration diagrams. Grid, time-line and fixed-geometry pipelines honour none: UML
sequence and timing, SysML 2 sequence, BPMN choreography and conversation, Service Blueprint and Journey. The
table in `LayoutEffectMatrix` is the single source for this.

Two options act on one diagram kind only: `labelMaxWidth` (SysML 2 state machines, wave 2D-b) and
`showSubjectEdges` (SysML 2 requirement diagrams, wave 2E-a); since wave 2E-b `actorSide` acts on SysML 2 use-case
diagrams only (`KUML-LAYOUT-W001` elsewhere, check 439 in `kuml validate`). `wrapColumns` and `sameLayer` also act on
block definition diagrams with edges: an edge between two members of one `sameLayer` group is withheld from the
layered engine and drawn straight between the facing sides of the aligned boxes (check 436 still warns).

In a SysML 2 use-case diagram with a subject frame, an explicit `actorSide = Both` assigns the actors to the two sides by
the position of their use cases (the actors whose use cases lie furthest left go to the left side) while the counts stay
as before, half of them per side. An explicit `aspectRatio` or `maxWidth` is evaluated there with the real geometry (row
gutter, frame padding, actor columns and the height of the actor stacks); without one of them the column count is
estimated as before.

=== UML class diagrams: wrap, grid and band (wave 2G-a)

* **Auto wrap.** If the widest layer of a class diagram with edges holds more than 6 nodes and none of `wrapColumns`,
  `aspectRatio` or `maxWidth` is given, the layer wraps into `ceil(sqrt(n))` columns (11 nodes: 4 columns). An explicit
  `wrapColumns` always wins.
* **Grid for wide generalisation fans.** A general classifier with more specialisations than one row holds (at least 4)
  gets them in a grid of the requested columns in declaration order, row by row. Boxes of one column share their left
  edge. Every generalisation edge is routed orthogonally and on its own: it leaves the specialisation, runs through the
  channel under its row to a vertical gutter between two columns (at least 32 px wide, one lane per edge), down the gutter to
  a collector channel above the general classifier, and ends at its own point. No edge touches a box. Only edges whose
  id starts with `gen::` (the default) are recognised; the other edges of a specialisation must be comment links, a
  horizontal flow (`direction = Right` / `Left`) keeps the engine routes, and foreign boxes in the way of the grid move sideways.
* **Band of edgeless classifiers.** Classes, interfaces and enumerations with no edge at all (a comment link counts as an edge)
  are withheld from the layered engine and stand in a band 40 px below the diagram, left-aligned, in declaration order,
  wrapped at the diagram's width but with at least 3 per row. Classifiers inside a package are not moved.

=== Labels and notes

Labels and notes are placed after the layout, and always in the same order: labels first, then notes, so a note
never covers a label that is drawn later.

* UML associations: name, multiplicity and role labels are placed by one cost-based placer (`LabelPlacer`).
  An association end whose multiplicity is written out (`multiplicity("1")` or `multiplicity = Multiplicity(1, 1)`) draws
  the label `1`; an end where no multiplicity is set draws none, because `1` is the default.
* SysML 2 IBD and BDD: connector labels are planned (`Sysml2EdgeLabelPlan`) before the notes; once the notes
  stand, the labels move away from them and from their anchor lines. The renderer draws each label exactly at its
  planned rectangle.
* SysML 2 state machines: the layout reserves the room a transition label needs between two layers (see Spacing between
  components); the label itself is placed afterwards from the final routes and never covers a state or another label
  unless no free position exists (`PlacedLabel.clean` is then `false`).
* Port labels and edge labels share one plan (`Sysml2DiagramLabelPlan`): one `LabelPlacer` run, arrow tips are
  12 x 12 px obstacles, a port label stays off the side where its edge docks, and the clearance to foreign lines is
  2 px. A port label longer than 24 characters wraps to at most two lines and is never cut. A label is drawn as one
  group: halo text directly under the fill text, same coordinates, no backdrop rectangle (two passes, because Batik
  ignores `paint-order`). The halo is 2 px wide for SysML 2 edge, port and pin labels.
* Port and pin labels (IBD ports, activity pins) come from the same plan, never from fixed positions. The candidates
  have a fixed rank: four positions outside the owner box (clockwise behind the port, counter clockwise behind it, then
  straight away from the port shifted left/up and right/down), then the same four inside. The label keeps 4 px from
  the port square and at least 2 px from every line, arrow tip, box, port and other label; a position straight in
  front of the edge that docks at the port is never used. A position inside the box is taken only when every outside
  position collides. Activity edge labels (`[Part]`) stand beside their line, not on it.
* IBD part boxes without nested frames carry a full-width title band (stereotype and name) as a hard obstacle, so a
  port label that has to go inside a box does not cover the title (if every position is blocked the least bad one is
  still taken). State machine transition labels keep 4 px from foreign edges; a label that crosses its own line is
  reported as not clean, wrapped narrower (0.6 of the normal width) and placed again, and the second plan is kept only
  if it leaves fewer unclean labels.
* Note anchors: a straight anchor that crosses nothing wins; otherwise one bend is allowed. An anchor that ends on a
  port arrives perpendicular and stays straight for the last 8 px, or reaches the side of the port square. A note keeps
  8 px from every part box and from every other note (covering a part or another note is excluded outright, the part never moves; since notes N2 a position on another note is never chosen, however crowded the anchor is: the nearest rings come first, then rows in a column beside the content, right and left alternating). The
  anchors of one connection get their own attach points at least 16 px apart; the anchor of the owner of a frame-less
  IBD ends on the border of a real part, never on a virtual box. An anchor does not cross a part or another note and
  runs no closer than 3 px side by side with the anchor of another note.
* Strict note placement of the structural SysML 2 diagrams (BDD including `allocate` edges, IBD, use case): a note keeps
  16 px from edges, nodes, ports, labels, titles and other notes, an anchor line keeps 6 px from foreign notes, nodes and
  ports (a soft cost reaches up to 12 px), and a note lies fully inside or fully outside a frame (the IBD owner frame, the
  use case subject frames). BDD and IBD prefer the sides across the layout flow (above and below for `Right`, beside for
  `Down`); this is a soft preference worth 40 px of anchor length, so a short anchor can win.
* Use case notes: a use case is an ellipse, so the dotted anchor line ends exactly on the ellipse outline (an axis projection of
  the note's exit when possible, otherwise the point on the ray from the centre) and never runs through the ellipse.
* SysML 2 IBD routing: connectors are routed around the parts of the diagram (`IbdObstacleRouter`: straight, L and Z
  candidates, then a grid A* with a hard node limit; 8 px clearance; deterministic). Neighbouring part ports keep a
  pitch of `max(24, label width + 8)` px on top and bottom sides and `max(24, line height + 6)` px on left and
  right sides; the box grows (capped) when a side is too short. An owner port sits on the frame side nearest to the
  connected part, at the projection of the connected port, at least 16 px from a corner. The SVG view box grows to
  contain every label, so its origin may be negative.
* ERM (Martin, Bachman, IDEF1X): relationship names and role labels are placed by the same placer; the
  cardinality glyphs are fixed obstacles.
* Service Blueprint: anchor lines of notes pick a free horizontal track (6 px raster, 6 px to every lane boundary,
  4 px to card edges, 6 px to other anchor tracks); when none is free the line runs in a channel below the lanes.
* SysML 2 PAR: binding labels are planned by `Sysml2DiagramLabelPlan.planParLabels` over the one `LabelPlacer`, before
  the notes (and again after them). A label keeps at least 2 px from every line, line end (12 x 12 px square), box,
  pin, box text and other label; the search runs outwards from the line up to 24 px; there are no leader lines. When
  every spot is taken the label sits on its own line with the halo and `KUML-LAYOUT-W005` is reported by `kuml render`
  and the Desktop. The halo is the 2 px two-pass text described above (Batik ignores `paint-order`). Pins and
  parameter rows come from one geometry (`ParConstraintGeometry`), so the SVG, the size estimate and the pin ends
  cannot drift apart. The layout engine reports the port or pin centre; when drawing, `PortEdgeClamp` clamps the edge
  onto the outer border of the port or pin. `PinSide.toPortFace(isOutput)` maps an action pin side to the port face
  (`Auto` by pin direction: input left, output right), so the ACT pin routing takes its face normals from
  `PortEdgeClamp.normal`; the arrowhead length is the one constant `PortEdgeClamp.ARROW_LEN_PX`.
* SysML 2 STM: transition labels are planned by `Sysml2DiagramLabelPlan.planStmLabels` over the one `LabelPlacer` (cost
  model `STM_COSTS`, candidates at positions along the arc length of the whole line, nearest the middle first, right of
  the direction of travel before left). Obstacles: states, pseudo-states and notes, the frame, header band, dividers and
  region names of composite states, every drawn line, the box of each arrow head (the source end a 12 px square) and the
  strip above the frame title; a label of an edge that does not run through a composite never enters it. Text is wrapped,
  never cut (see the STM chapter of the SysML 2 reference). Parallel line segments and the ends at one side of a
  state keep 16 px (`Spacing.edgeToEdgeBetweenLayers`, `StmEndpointSpread`). The halo is the same 2 px two-pass text.
* Other SysML 2 diagram kinds (SEQ, REQ, UC) keep their own label placement; ACT plans pin labels and edge labels together (`Sysml2DiagramLabelPlan.planActLabels`).

== SysML 2 layout hints

Every SysML 2 diagram accepts a `layout { }` block with coarse steering hints. There are deliberately
no pixel positions and no pairwise relative constraints.

[source,kotlin]
----
reqDiagram("Requirements") {
    // include(...)
    layout {
        direction = Right      // Down (default), Right, Up, Left
        wrapColumns = 4        // at most 4 nodes per layer
        sameLayer(a, b)        // same layer
        first(root)            // first layer
        last(leaf)             // last layer
    }
}
----

* `wrapColumns` moves the nodes of an over-full layer (declaration order) into additional layers.
  Layers are computed by longest-path layering; back edges are ignored.
* `first` and `last` use ELK's layer constraints when no wrap/`sameLayer` is given and the edges allow it
  (a `first` node must have no incoming and a `last` node no outgoing edge, otherwise the pin is dropped).
  Together with wrapping they are expressed as layer indices.
* `sameLayer` members of a state machine are centred on the flow axis (same `y` centre for `direction = Down`,
  same `x` centre for `Right`, 0.5 px). An edge between two members is drawn straight between the facing sides
  and does not pull the members into different layers. If the members cannot share a layer (for example because of
  a `first` constraint) the group is left as laid out and a warning is logged.
* In a state machine (SysML 2 STM and UML) the initial pseudo-state always gets a layer of its own in front of all
  other states, also in a diagram without a `layout { }` block. Edges that close a cycle are reversed by the engine,
  never the edge out of the initial. Afterwards the initial is placed in three steps, the first clear spot wins:
  (1) 36 px in front of everything (all nodes and edge bends), centred on its target; (2) 36 px directly in front of
  the target; (3) the engine position stays. The edge is a straight two-point line. A spot is clear when the dot and
  its edge keep 8 px to every other node and edge. A frame around the machine (UML) is refitted around the moved dot.
  Edge labels are placed later and are not part of that check. Initial pseudo-states inside a composite state or
  region are left to the engine. UML state machines keep their nodes in a compound frame, where layer hints are
  ignored, so there the cycle-breaking priority and the placement above do the work.
* Layer hints are honoured for nodes that are not inside a compound group. ELK ignores them inside
  compounds and reports `hint.ignored.layerInCompound`.
* Sequence diagrams ignore all hints (lifeline order is the declaration order); `kuml validate` warns (`LAYOUT412`).
* The grid engine and the WebAssembly playground do not evaluate these hints.
* Swimlane (partition) activity diagrams are drawn top to bottom only; another `direction` is reported as `LAYOUT433`.
* Checks: `LAYOUT431` unknown id, `LAYOUT432` `wrapColumns` outside 1..32, `LAYOUT434` too many groups/ids,
  `LAYOUT435` id in `first` and `last`, `LAYOUT436` connected elements in one `sameLayer` group,
  `LAYOUT437` `maxWidth`/`aspectRatio`/`labelMaxWidth` out of range, `LAYOUT438` `showSubjectEdges` on a diagram
  that is not a requirement diagram (wave 2E-a), `LAYOUT443` `showSubjectEdges = true` but the subject of a requirement
  is not shown in the diagram (warning; no edge can be drawn), `LAYOUT444` group-local `wrapColumns` outside 1..32.

=== Requirement groups as a grid (wave 2E-a)

ELK ignores layer hints for nodes inside compound groups, so a requirement diagram with `group { }` frames used to
lose `wrapColumns` and `sameLayer`. A requirement diagram that has groups **and** one of `wrapColumns`, `aspectRatio`,
`maxWidth` or a `sameLayer` of groups is laid out as a grid instead (without any of these options the node placement is
the same as before):

[source,kotlin]
----
reqDiagram("Platform") {
    val functional = group("Functional") { include(boot); include(update) }
    val safety = group("Safety") { include(auth); group("Fail-safe") { include(failSafe) } }
    val perf = group("Performance") { include(latency) }
    val ops = group("Operations") { include(logs) }
    layout {
        wrapColumns = 2              // 2 x 2 grid of frames
        sameLayer(perf, ops)         // these two frames share a row
        showSubjectEdges = false     // default; true draws a <<subject>> edge per subjectRef
    }
}
----

* The top-level groups, in declaration order, are the cells of the grid, plus one trailing cell for requirements that
  are in no group. Cells are aligned top left; the gap is 40 px.
* The column count is `wrapColumns` (at most the number of cells). Without it the grid picks the count whose canvas
  is closest to `aspectRatio` (default 1.6; the block rail counts), within `maxWidth`; ties go to fewer columns.
* The same rule applies inside every group: cards (in `include` order), then child groups, fill the group row by row.
  The `include` order is the reading order.
* A group can set its own column count with a group-local `layout` block; it applies to the members of exactly that
  group (cards and child groups) and wins over the diagram value there. The top-level grid keeps using the diagram
  value. The block accepts `wrapColumns` only (range 1..32, `LAYOUT444` otherwise). A group-local value alone, without any
  diagram `layout`, is enough to switch the grid on:
+
[source,kotlin]
----
group("Safety") {
    include(auth); include(audit); include(failSafe)
    layout { wrapColumns = 3 }   // three cards per row inside this frame
}
----
* A note whose anchors are all requirements of one group stands inside that frame: the frame reserves a strip below its
  cards for it and the note goes there when its anchor line can be routed. No note covers a frame line (an 8 px band on
  each side is kept free). A note anchored in several groups, or whose strip position has no clear anchor line, is
  placed by the general rule and can end up outside the frame.
* A requirement that is `include`d in two groups stands in the first one in declaration order only; the layout reports
  `KUML-LAYOUT-W007`.
* `direction = Right` transposes the grid (frames are filled column by column, so `wrapColumns = 2` gives
  A C / B D); `Up` and `Left` mirror rows and columns.
* `sameLayer(groupA, groupB)` (group handles or the ids `group:<name>`) puts the groups in one row. If that row is
  longer than the column count it is widened and `KUML-LAYOUT-I001` (information, not an error) says so.
* Blocks (`partDef`) that are in no group stand on a rail left of the grid (above it with `direction = Right`
  or `Left`), each at the mean height of the requirements it satisfies, at least 24 px apart.
* Every edge is routed around the cards (orthogonal, inside the content box). Every requirement diagram, grid or not,
  gets spread edge ends (at least 12 px between ends on one side, 8 px from the corners) and nudged parallel
  segments (parallel segments of different edges that are closer than 8 px move to a 10 px pitch).
* Determinism: the result depends only on the model. The engine seed is fixed, the model order is the tie-breaker,
  the grid code iterates only ordered collections, and two renders of one script are byte-identical.
* Labels of several edges between the same pair of nodes (for example `derive` and `trace`) that would overlap are stacked
  across the edge direction, `derive` first, then `trace`, then the rest by edge id; labels that do not collide stay where
  they are.
* Edge labels avoid group frames; a label that finds no free spot takes the cheapest position and is never dropped. There is one `<<satisfy>>`
  label per source block (on the satisfy edge with the smallest id), and containment has no text label.

=== Use-case diagrams with a subject frame (wave 2E-b)

A use-case diagram with at least one `subject("...") { }` frame is laid out as a grid (`UcFrameGrid`) instead of by the
layered engine:

* The use cases of a frame are packed in `include` order. `wrapColumns` gives the column count exactly; without it the
  smallest count whose picture (frame plus the actor columns) is at most 1.6:1 wide is chosen (the picture target of
  `aspectRatio` and `maxWidth` apply as in the requirement grid). If that cannot be reached, `KUML-LAYOUT-W003` says so.
* Actors stand outside the frame. `actorSide = ActorSide.Auto` (default): up to two actors on the left, more are split
  (the first half left, the rest right); `Left`, `Right` and `Both` are explicit. Within one side the actors are ordered
  by the mean height of the use cases they touch (ties: declaration order).
* All lines are routed orthogonally around the final nodes; the ends on one side of a node are spread evenly. At a use
  case the ends stay in the middle band of the side (60 percent) and finish on the ellipse outline, not on its bounding
  box.
* Lines of different edges are separated where possible: parallel segments that overlap are moved to at least 8 px (12 px
  preferred) from each other, never onto or across the border of the subject frame, the gap between actor column and frame grows with the number of lines of the actors, and a
  jog shorter than 16 px is straightened (a jog that cannot be, gets sharp corners instead of a bump). The first and the
  last segment of a line stay on their port. The limits: diagrams with more than 2000 line segments are left as routed,
  the separation runs at most three passes, and a conflict that has no free lane stays (overlapping lines are then
  possible).
* A line between two use cases of one column with other use cases in between (typically `extend` and `include`) runs as a
  C along the column with two bends, on the side whose gutter is free, instead of detouring around the use cases in
  between. Lines between neighbours of one row keep their U through the gap below the row.
* Without a subject frame the layered engine is used as before.

[source,kotlin]
----
ucDiagram("Web shop") {
    // ...
    layout {
        wrapColumns = 4
        actorSide = ActorSide.Auto   // Left, Right, Both
    }
}
----

=== Example: a wide requirement diagram

Without a hint, twelve requirements are laid out in one very wide row:

[source,kuml]
----
import dev.kuml.sysml2.RequirementPriority
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model("Platform Requirements") {
    val reqs = listOf(
        "Boot" to "The platform shall boot within 5 seconds.",
        "Update" to "Updates shall install without user interaction.",
        "Rollback" to "A failed update shall roll back automatically.",

=== Activity lanes, regions and merges (wave 2F)

For activity diagrams that flow down and have swimlanes the layout engine sees one flat flow graph; the post-pass
`Sysml2LayoutBridge.normalizeActLayout` (called by the SVG renderer, not by `LayoutSpecRunner`) then does the rest:

. the layers come from the flow graph (depth-first back-edge detection from the sources in declaration order, longest
  path); the engine's own layering is not used, so a cycle cannot turn the main flow upside down;
. every `sameLayer` group moves to the deepest layer of its members, followers move down, the members share a centre
  line;
. a lane is as wide as its widest row (sum of node widths plus 24 px gaps, plus 2 x 24 px, at least 160 px, plus a
  16 px corridor if a back edge leaves it); all lanes are bands of equal height below a 28 px header;
. non-members of an interruptible region are pushed sideways out of its frame (at most 8 rounds);
. every flow is routed again, orthogonally, around foreign nodes; collinear segments of different edges keep 12 px.

If a region frame still overlaps a non-member afterwards, the result carries `KUML-LAYOUT-W006`.

=== Sequence fragments (wave 2F)

The lifelines of a sequence diagram are placed 24 px from the top (8 px layout margin plus the 16 px canvas padding);
the canvas ends 24 px below the lowest lifeline end. The width of a fragment frame comes from the lifelines it covers
(`coveredLifelines`), its height from its last content; `SeqRowOffsets` opens the gap of 12 px between consecutive
fragments and the room for a self loop in the last row. The same row model is used by messages, activation bars, frames
and notes.

=== Sequence notes (Nacharbeit 39)

Notes of UML and SysML 2 sequence diagrams are placed after the layout by `SeqNotePlacer`, against what the renderer
really draws (the draw functions are run into a scratch builder and read back): stems, heads, activation bars (SysML 2),
`ref` frames, fragment frames, operator tags, guards, operand separators, message lines and labels. The candidate order is
fixed: the inner column right of the anchor, the inner column left, the right margin, the left margin; vertically a note
starts at the anchor height and moves at most three message rows (six in the margins). A note keeps 16 px from everything
drawn and from other notes. A participant is anchored on its stem by a horizontal line; a message by a corridor 8 px
below its line (or a vertical line from a note below it). An anchor line never crosses a foreign note, head, bar, tag,
guard, label or operand separator; crossings of foreign stems, messages and frame edges are allowed but minimised. A note
across several lifelines goes to the margin of its outermost lifeline. If no column is admissible, the note goes to the
right margin as a last resort (`degraded`); it never overlaps anything. In dense diagrams the margin column grows
downwards, and anchor lines get long.

== When the engine can't honour a hint

Conflicts produce a `LayoutWarning` in `LayoutResult.warnings`:

[cols="1,3"]
|===
| Warning code | When

| `hint.conflict.gridSlot`
| Two elements want the same hard-pinned slot. Loser is shifted right; warning lists the
  affected node IDs.

| `hint.unfulfilled.relativeConstraint`
| Preferred slot from a relative constraint was occupied. Fallback to next free slot.

| `hint.deferred.relativeConstraint`
| Anchor element wasn't yet placed when the constraint was evaluated.

| `KUML-LAYOUT-W006`
| An interruptible-region frame still overlaps a node that is not a member of the region (activity diagram, wave 2F).
  The warning lists the nodes.

| `KUML-LAYOUT-W007`
| A requirement diagram lists one requirement in two groups. It stands in the first group in declaration order only
  (Nacharbeit 55).

| `engine.performance.large_graph`
| Graph exceeds the engine's recommended max (`maxRecommendedNodes`). Suggest a different
  engine.
|===

The CLI prints warnings after a render so you can iterate on hints without staring at SVG
diffs.

== Edge routing

Four edge styles, all engines support all four:

[cols="1,3"]
|===
| Style | Behaviour

| `Direct`
| Straight line between source and target.

| `OrthogonalRounded` (default)
| Horizontal-vertical-horizontal (or vertical-horizontal-vertical) route with rounded corners.

| `TreeRounded`
| V-shape route with top-down bias — looks tidy for hierarchies. V1.1.12 falls back to
  `OrthogonalRounded`; V1.2 adds tree-aware routing proper.

| `Bezier`
| Cubic Bezier with two control points offset perpendicular to the direct line.
|===

Set per edge:

[source,kotlin]
----
association(source = a, target = b) {
    routeStyle = EdgeRouteStyle.Direct
}
----

Or globally for a diagram:

[source,kotlin]
----
classDiagram(name = "X") {
    layoutHints {
        defaultEdgeStyle = EdgeRouteStyle.Bezier
    }
    // ...
}
----

== Performance characteristics

[cols="1,2,2"]
|===
| Size | `elk.layered` | `kuml.grid`

| ≤ 100 nodes
| < 100 ms
| < 10 ms

| ≤ 500 nodes
| < 1 s
| < 100 ms

| > 500 nodes
| Still works, may be slow
| Emits `engine.performance.large_graph` warning; suggests ELK
|===

The grid engine is deterministic — same input + same seed = byte-identical layout. ELK is
also seeded but has more internal randomness in its heuristics; outputs are stable but
small floating-point differences may appear across JVM versions.

== Authoring your own engine

Implement `KumlLayoutEngine` (pure Kotlin recommended for native-image compatibility),
then provide a `KumlLayoutEngineProvider`:

[source,kotlin]
----
class CircularLayoutEngine : KumlLayoutEngine {
    override val id = LayoutEngineId("circular")
    override val capabilities = LayoutCapabilities(
        deterministic = true,
        supportedDiagramKinds = setOf(DiagramKind.UmlClass, DiagramKind.Generic),
        // ...
    )
    override fun layout(graph: LayoutGraph, hints: LayoutHints): LayoutResult {
        // ... place nodes on a circle, route edges, return LayoutResult
    }
}

class CircularLayoutEngineProvider : KumlLayoutEngineProvider {
    override val id = LayoutEngineId("circular")
    override fun engine() = CircularLayoutEngine()
}
----

Register via `META-INF/services/dev.kuml.layout.KumlLayoutEngineProvider`:

[source]
----
com.example.CircularLayoutEngineProvider
----

`LayoutEngineRegistry.loadFromClasspath()` discovers it. CLI flag `--engine circular`
selects it.
