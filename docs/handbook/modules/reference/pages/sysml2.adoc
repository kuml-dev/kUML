= SysML 2 DSL Reference
:description: Every SysML 2 diagram type supported by kUML, with the DSL syntax and simulation notes.

SysML 2 is kUML's second modelling language — a domain-specific language for systems
engineering defined by OMG SysML v2.0. While the UML DSL focuses on software structure
and behaviour, SysML 2 is purpose-built for modelling physical and cyber-physical systems:
requirements, functional breakdown, parametric constraints, and executable state behaviour.

The SysML 2 DSL entry point is `sysml2Model`:

[source,kotlin]
----
sysml2Model("SystemName") {
    // diagram builders go here
}
----

Every diagram builder is also usable at top level without the `sysml2Model` wrapper — the
wrapper is only needed when a single script contains multiple SysML 2 diagrams.

== Diagram types at a glance

[cols="1,2,2,1"]
|===
| Abbreviation | Full name | Builder | Use it for

| BDD
| Block Definition Diagram
| `partDef(name) { ... }` + `bdd(name) { include(...) }`
| Structural decomposition: blocks, value properties, ports, part/reference associations.

| IBD
| Internal Block Diagram
| `partDef(name) { part(...); connect(...) } }` + `ibd(name, owner)`
| Internal wiring: parts within a block, connectors between ports, item flows.

| UC
| Use Case Diagram
| `ucDiagram(name) { ... }`
| Actor goals: system actors, use cases, include/extend relationships.

| REQ
| Requirements Diagram
| `reqDiagram(name) { ... }`
| Stakeholder requirements: requirements, derives, satisfies, verifies, contains links.

| STM
| State Machine Diagram
| `stateDef(name)` + `transition(...)` + `stmDiagram(name) { include(...) }`
| Executable discrete behaviour: states, transitions, trigger/guard/action triples.

| ACT
| Activity Diagram
| `actionDef(name)` + control flow + `actDiagram(name) { include(...) }`
| Executable workflow: actions, decisions, forks/joins, item flows, object flows.

| SEQ
| Sequence Diagram
| `lifelineDef(name)` + `message(...)` + `seqDiagram(name) { include(...) }`
| Time-ordered interaction between blocks: lifelines, messages, combined fragments.

| PAR
| Parametric Diagram
| `constraintDef(...)` + `bind(...)` + `parDiagram(name) { include(...) }`
| Constraint properties: parameters, equations, numerical constraints.

| PKG
| Package Diagram
| `pkg(name) { ... }` + `imports(...)` + `packageDiagram(name) { include(...) }`
| Model organisation: nested packages, imports, views and viewpoints (wave 2I-a).
|===

== Block Definition Diagrams (BDD)

BDD is the SysML 2 analogue of the UML class diagram. The central classifier is `block`.
Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/03 SysML 2 BDD – Hybrid Vehicle.md`):

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "VehicleSystem") {
    val massType = attributeDef(name = "Mass")
    val powerType = attributeDef(name = "Power")

    // Abstract base definition — cannot be instantiated directly
    val powertrain = partDef(name = "Powertrain", isAbstract = true) {
        attribute(name = "ratedPower", typeId = powerType.id)
    }

    val vehicle = partDef(name = "Vehicle") {
        attribute(name = "mass", typeId = massType.id)
    }

    // Specialisation: Engine is a concrete Powertrain flavour
    val engine = partDef(name = "Engine", specializesId = powertrain.id) {
        attribute(name = "ratedPower", typeId = powerType.id)
    }

    bdd(name = "Vehicle BDD") {
        include(definition = powertrain)
        include(definition = vehicle)
        include(definition = engine)
    }
}
----

Key BDD elements:

[cols="1,2"]
|===
| Element | Notes

| `block(name)`
| The top-level SysML 2 classifier. Supports `valueProperty`, `partProperty`, `referenceProperty`, `port`, `operation`, `constraint`.

| `valueProperty(name, type)`
| A typed scalar or structured value. `unit` is optional — attaches a unit annotation.

| `partProperty(name, type)`
| A typed part (composition by reference to another block type).

| `port(name, direction)`
| `PortDirection.In`, `.Out`, or `.InOut`.

| `composition(parent, child, roleName)`
| Whole/part relationship. Renders as filled diamond.

| `association(source, target)`
| Non-ownership association. Block args or string names.
|===

== Internal Block Diagrams (IBD)

IBD shows the internal wiring of a single block context: parts, ports, and connectors
between them. Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/27 SysML 2 IBD – Hybrid Vehicle Wiring.md`):

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "HybridVehicleSystem") {
    val powerLine  = connectionDef(name = "PowerLine")
    val driveshaft = connectionDef(name = "Driveshaft")

    val dcPort    = portDef(name = "DcPort")
    val shaftPort = portDef(name = "ShaftPort")

    val battery = partDef(name = "Battery") {
        port(name = "dcOut", typeId = dcPort.id)
    }
    val electricMotor = partDef(name = "ElectricMotor") {
        port(name = "dcIn",  typeId = dcPort.id)
        port(name = "shaft", typeId = shaftPort.id)
    }
    val iceEngine = partDef(name = "InternalCombustionEngine") {
        port(name = "shaft", typeId = shaftPort.id)
    }
    val powerSplitter = partDef(name = "PowerSplitter") {
        port(name = "emIn",  typeId = shaftPort.id)
        port(name = "iceIn", typeId = shaftPort.id)
    }

    val hybrid = partDef(name = "HybridVehicle") {
        part(name = "battery",       typeId = battery.id)
        part(name = "electricMotor", typeId = electricMotor.id)
        part(name = "iceEngine",     typeId = iceEngine.id)
        part(name = "powerSplitter", typeId = powerSplitter.id)

        connect(
            name = "batteryToMotor",
            typeId = powerLine.id,
            sourceEndId = "HybridVehicle::battery::dcOut",
            targetEndId = "HybridVehicle::electricMotor::dcIn",
        )
        connect(
            name = "motorToSplitter",
            typeId = driveshaft.id,
            sourceEndId = "HybridVehicle::electricMotor::shaft",
            targetEndId = "HybridVehicle::powerSplitter::emIn",
        )
        connect(
            name = "iceToSplitter",
            typeId = driveshaft.id,
            sourceEndId = "HybridVehicle::iceEngine::shaft",
            targetEndId = "HybridVehicle::powerSplitter::iceIn",
        )
    }

    ibd(name = "HybridVehicle — internal block diagram", owner = hybrid)
}
----

Connectors end on the outer border of the port square, perpendicular to its side. A stub of arrowhead length is
only drawn at an end that carries an arrowhead (item flows); plain connectors touch the port directly.

=== Attribute compartment

A part box lists the attributes of its definition below a rule, as `name : Type = value` (`= value` only when a value
exists; a redefinition on the part usage supplies it), at most eight lines and then `... n more`.
`ibd(name, owner = x, showAttributes = false)` switches the compartment off.

=== Connection line style

[source,kotlin]
----
connectionDef(name = "Feed", style = ConnectionLineStyle.DASHED, color = "#1D2968")
----

`style` is `SOLID` (default), `DASHED`, `DOTTED` or `DASH_DOT`; `color` is `#RRGGBB` or omitted (theme colour). Every
connection typed by the definition is drawn that way. There is no legend.


=== IBD findings

[cols="1,1,3",options="header"]
|===
| Code | Severity | Rule
| `IBD501` | Warning | an end of a `connect(...)` or flow does not resolve to a part, port or owner port; the edge is not drawn
|===

Use `Owner::port`, `part.port` or a bare owner-port name as an end. `kuml validate`, the Desktop validate and the
Desktop render warnings report `IBD501`.

== Use Case Diagrams (UC)

SysML 2 use case syntax mirrors UML use case: actors, use cases, `include`/`extend`
relationships. Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/05 SysML 2 UC – Library System.md`):

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "LibrarySystem") {
    val reader = actorDef(name = "Reader")
    val librarian = actorDef(name = "Librarian")
    val paymentSystem = actorDef(name = "PaymentSystem")

    val borrowBook = useCaseDef(name = "BorrowBook")
    val returnBook = useCaseDef(name = "ReturnBook")
    val payLateFee = useCaseDef(name = "PayLateFee")
    val authenticate = useCaseDef(name = "Authenticate")

    ucDiagram(name = "Library — top-level use cases") {
        include(definition = reader)
        include(definition = librarian)
        include(definition = paymentSystem)
        include(definition = borrowBook)
        include(definition = returnBook)
        include(definition = payLateFee)
        include(definition = authenticate)

        association(actor = reader, useCase = borrowBook)
        association(actor = reader, useCase = returnBook)
        association(actor = reader, useCase = payLateFee)
        association(actor = librarian, useCase = borrowBook)
        association(actor = paymentSystem, useCase = payLateFee)

        // «include»: target is always executed as part of source
        include(source = borrowBook, target = authenticate)
        include(source = returnBook, target = authenticate)

        // «extend»: target's behaviour is optionally extended by source
        extend(source = payLateFee, target = returnBook)
    }
}
----

=== System boundaries, actor generalisation and descriptions

`subject("Name") { include(useCase) }` draws a system boundary. The use cases inside the block become
children of the frame; actors never do, so they always stay outside. Several frames sit side by side.
`generalize(specific, general)` draws an actor generalisation (solid line, hollow triangle at the general
actor). `useCaseDef(description = "...")` shows an italic description (at most four lines, longer text is
cut with an ellipsis and kept in the tooltip) inside the ellipse.

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model("Library") {
    val user = actorDef("User")
    val reader = actorDef("Reader")
    val librarian = actorDef("Librarian")
    val borrow = useCaseDef("Borrow Book", description = "A reader borrows a book for up to four weeks. The system checks the account and records the loan.")
    val auth = useCaseDef("Authenticate")
    val fee = useCaseDef("Pay Late Fee")
    val manage = useCaseDef("Manage Catalogue", description = "Add, change or remove titles in the catalogue of the library system.")
    val export = useCaseDef("Export Report")
    ucDiagram("Library system") {
        include(user)
        include(reader)
        include(librarian)
        include(borrow)
        include(auth)
        include(fee)
        include(manage)
        include(export)
        generalize(reader, user)
        generalize(librarian, user)
        association(reader, borrow)
        association(librarian, manage)
        association(librarian, export)
        include(borrow, auth)
        extend(fee, borrow)
        subject("Lending") {
            include(borrow)
            include(auth)
            include(fee)
        }
        subject("Administration") {
            include(manage)
            include(export)
        }
    }
}
----

== Requirements Diagrams (REQ)

Requirements diagrams trace stakeholder needs through derivation, satisfaction,
verification, and containment. Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/08 SysML 2 REQ – Vehicle Requirements.md`):

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "VehicleRequirements") {
    val topSpeed = requirementDef(
        name = "TopSpeedRequirement",
        reqId = "R-001",
        text = "The vehicle shall reach at least 180 km/h on flat road",
        subject = "Vehicle",
    )
    val curbWeight = requirementDef(
        name = "CurbWeightRequirement",
        reqId = "R-002",
        text = "The vehicle curb weight shall not exceed 1500 kg",
        subject = "Vehicle",
    )
    val fuelEfficiency = requirementDef(
        name = "FuelEfficiencyRequirement",
        reqId = "R-003",
        text = "The vehicle shall consume less than 4 l/100km combined",
        subject = "Vehicle",
    )
    val emissions = requirementDef(
        name = "EmissionsRequirement",
        reqId = "R-004",
        text = "The vehicle shall comply with Euro 7 emissions standards",
        subject = "Vehicle",
    )
    val nox = requirementDef(
        name = "NOxRequirement",
        reqId = "R-005",
        text = "NOx emissions shall not exceed 30 mg/km",
        subject = "Vehicle",
    )

    val vehicle = partDef(name = "Vehicle")
    val verifyTopSpeed = useCaseDef(name = "VerifyTopSpeed")

    reqDiagram(name = "Vehicle — top-level requirements") {
        include(definition = topSpeed)
        include(definition = curbWeight)
        include(definition = fuelEfficiency)
        include(definition = emissions)
        include(definition = nox)
        include(definition = vehicle)
        include(definition = verifyTopSpeed)

        satisfy(source = vehicle, requirement = topSpeed)
        satisfy(source = vehicle, requirement = curbWeight)
        satisfy(source = vehicle, requirement = fuelEfficiency)

        verify(source = verifyTopSpeed, requirement = topSpeed)

        // Endgeschwindigkeit vs. Verbrauch ist ein klassischer Trade-off
        derive(source = topSpeed, target = fuelEfficiency)

        contains(parent = emissions, child = nox)
    }
}
----

=== Requirement attributes, test cases, groups and relationships

`requirementDef` accepts `priority` (`HIGH`, `MEDIUM`, `LOW`), `status` (`DRAFT` ... `VERIFIED`), `source`,
`isAssumption = true` (dashed border, `<<assumption>>`) and `subjectRef` (the id of the constrained element;
the card shows a line `subject: <Name>`). Since wave 2E-a a `<<subject>>` edge is drawn only with
`layout { showSubjectEdges = true }` (default `false`, and never for a pair that already has a `satisfy` edge);
**migration:** diagrams that relied on the automatic subject edge add that one line to their `layout` block.
The free-text `subject` stays available. Titles are wrapped
instead of truncated; the box width is between 160 and 240 px and the height grows with the content.
`testCaseDef` adds a verification element (rounded box, `<<testCase>>`). `group("Name") { ... }` draws a framed
group with a name tab; groups nest up to three levels and an element belongs to at most one group.
New relationships: `refine(source, requirement)`, `trace(source, target)` and `copy(slave, master)`.

[source,kuml]
----
import dev.kuml.sysml2.RequirementPriority
import dev.kuml.sysml2.RequirementStatus
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model("Vehicle Requirements") {
    val car = partDef("Car")
    val brakes = partDef("BrakeSystem")
    val top = requirementDef(
        "TopSpeed",
        reqId = "R-001",
        text = "The vehicle shall reach at least 180 km/h on flat road within 30 seconds.",
        priority = RequirementPriority.HIGH,
        status = RequirementStatus.APPROVED,
        source = "Marketing, Product Brief 2026",
        subjectRef = "Car",
    )
    val stop = requirementDef(
        "StoppingDistanceFromHundredKilometresPerHourOnDryAndWetRoadSurfaces",
        reqId = "R-002",
        text = "The vehicle shall stop from 100 km/h within 36 metres on a dry road.",
        priority = RequirementPriority.MEDIUM,
        status = RequirementStatus.DRAFT,
    )
    val stopCopy = requirementDef(
        "StoppingCopy",
        text = "The vehicle shall stop from 100 km/h within 36 metres on a dry road.",
    )
    val dry = requirementDef(
        "DryRoadAssumption",
        text = "Tests are run on dry asphalt at 20 degrees Celsius.",
        isAssumption = true,
    )
    val abs = requirementDef("AbsRequired", text = "ABS is mandatory.", priority = RequirementPriority.LOW)
    val speedTest = testCaseDef("TopSpeedTest", text = "Accelerate on the test track.")
    val driving = useCaseDef("DriveFast")
    reqDiagram("Vehicle requirements") {
        include(car)
        include(brakes)
        include(driving)
        include(top)
        include(speedTest)
        group("Performance") {
            include(top)
            group("Braking") {
                include(stop)
                group("Details") {
                    include(stopCopy)
                    include(abs)
                }
            }
        }
        include(dry)
        satisfy(car, top)
        satisfy(brakes, stop)
        verify(speedTest, top)
        derive(abs, stop)
        contains(stop, abs)
        refine(driving, top)
        trace(dry, stop)
        copy(stopCopy, stop)
    }
}
----

==== Containment, external requirements (wave 2E-a)

`contains(parent, child)` is drawn as a solid line with a circled plus (&#8853;) at the parent, without a text
label (the former `<<containment>>` label sat on frames and hid text). Legend: &#8853; = the owner of the
requirement it touches; dashed with an open head = `satisfy`, `verify`, `deriveReqt`, `refine`, `trace`, `copy`.

A requirement that lives in another document is referenced with `externalRequirement(reqId, source, text?)`:

[source,kotlin]
----
val ext = externalRequirement("PAL-FB-007", source = "Dokument 11", text = "Restore within one hour.")
reqDiagram("Doc 12") {
    include(ext)                 // dashed card, <<external>>, "source: Dokument 11"
    derive(localRequirement, ext)
}
----

The stub has the id `ext:<reqId>`; calling it twice with the same `reqId` returns the same stub. It may be an end
of `copy` and `derive`. The reference is by `reqId` inside one script; a shared workspace model library across
documents does not exist yet.

==== Structural checks (`kuml validate`, REQ and UC)

[cols="1,1,4"]
|===
|Code |Severity |Rule
|201 |Error |`copy` endpoint is not a requirement
|202 |Error |`copy` slave and master have different `text`
|203 |Error |`subjectRef` does not resolve to a definition
|204 |Error |Groups nested deeper than 3 levels (or a group cycle)
|205 |Error |A use case is inside more than one subject frame
|206 / 207 |Error |Actor generalisation cycle / a side is not an actor
|208 |Error |A requirement is a member of more than one group
|209-212 |Error |Limits: title 200, requirement text 2000, source 200, use-case description 1000 characters
|213 / 214 |Error |More than 64 groups / 16 subject frames in one diagram
|215 |Warning |`verify` source is neither a test case nor a use case
|216 |Warning |`refine` target is not a requirement
|217 |Hint |Use-case description longer than four lines (truncated in the diagram)
|218 |Warning |Two requirements of the model share a `reqId` but have different text (whitespace is normalised, case is not; pairs joined by `copy` are left to 202). The check covers the model of one script; `kuml validate` reads one file, so a comparison across files is not possible yet.
|===

`trace` is intentionally unchecked. Renderers additionally cut over-long text defensively, so a plain
`kuml render` without `validate` cannot blow up the layout.

== State Machine Diagrams (STM)

STM is the primary entry point for executable behaviour in SysML 2. kUML implements
SysML 2 state machines on top of the same runtime as UML state machines — `kuml simulate`
works for both.

Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/04 SysML 2 STM – Traffic Light.md`):

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "TrafficLight") {
    val initial = stateDef(name = "Initial", isInitial = true)
    val red = stateDef(
        name = "Red",
        entryAction = "switchLights('red')",
        exitAction = "logTransition('red')",
    )
    val green = stateDef(
        name = "Green",
        entryAction = "switchLights('green')",
        doAction = "tickTimer()",
    )
    val yellow = stateDef(
        name = "Yellow",
        entryAction = "switchLights('yellow')",
    )
    val off = stateDef(name = "Off", isFinal = true)

    transition(name = "init", source = initial, target = red)
    transition(name = "redToGreen", source = red, target = green, trigger = "timer60s")
    transition(name = "greenToYellow", source = green, target = yellow, trigger = "timer45s")
    transition(name = "yellowToRed", source = yellow, target = red, trigger = "timer5s")
    transition(
        name = "powerOff",
        source = red,
        target = off,
        trigger = "powerOff",
        guard = "!emergency",
        effect = "shutdownLights()",
    )

    stmDiagram(name = "TrafficLight — phase cycle") {
        include(state = initial)
        include(state = red)
        include(state = green)
        include(state = yellow)
        include(state = off)
    }
}
----

Run the machine with a JSON events file:

[source,bash]
----
kuml simulate thermostat.kuml.kts --events thermostat-events.json
----

See xref:simulate.adoc[State-Machine Simulation] for the full events/trace format, golden
trace verification, and interactive REPL mode.

NOTE: `kuml simulate` supports both UML `stateDiagram { stateMachine { ... } }` and
SysML 2 `sysml2Model { stateDef / transition }` syntaxes. The underlying runtime is shared.

=== Composite states, regions and pseudo-states

State machines can be nested. A state is made composite by giving other states a `parent`; orthogonal regions
are declared with `region(owner, "name")` and children pick one with `region = r`.

[source,kotlin]
----
sysml2Model("Pipeline") {
    val par = stateDef("Parallel")
    val left = region(par, "Left")
    val right = region(par, "Right")
    val load = stateDef("Load", parent = par, region = left)
    val fetch = stateDef("Fetch", parent = par, region = right)
    val split = fork("Split")
    val merge = join("Merge")
    history("H", deep = true, parent = par)   // H* ; parent is mandatory
    choice("Decide"); junction("Merge2")
    // ... transitions as usual
    stmDiagram("Pipeline") { include(par); include(split); include(merge) }
}
----

Including a composite shows all its descendants; including only a child also shows its ancestors.
`region(...)` replaces the owner definition in the model, so refer to states by id afterwards, not through an
old variable.

Transitions may end on a composite frame. Transitions between a composite and one of its own descendants are
routed to the frame and flagged by warning 115.

==== Transition labels

A label reads `[name:] trigger[, timer] [guard] / effect`. It is never cut: text wider than the wrap width (default 220 px,
`layout { labelMaxWidth = 120..400 }`) wraps at spaces, then after `,` and `(` and around `&&` / `||`, and only for a
word that is still too long inside the word with a `-`; every part (name, event, guard, effect) starts on its own line
once the label wraps. A prose guard stays italic on every line. The full text is also the `<title>` of the label group
in the SVG. A label is drawn as halo text (2 px, background colour) under the fill text, with no backdrop rectangle, so
it never hides a line or an arrow head. The planner puts the label beside a long, unshared segment of its own line, right
of the direction of travel first, and never on another line, arrow head, state, composite header or label. Two parallel
segments and two line ends at one side of a state keep 16 px.

`transition(name = "T37", ..., showName = true)` prints the transition name as `T37:` in front of the label (default
`false`; the DSL printer writes it only when `true`).

==== Structural checks (`kuml validate`)

[cols="1,1,4"]
|===
|Code |Severity |Rule
|101 |Error |Initial state has an incoming transition
|102 |Error |Final state has an outgoing transition
|103 / 104 |Error |Fork targets / join sources are not in pairwise different regions
|105 / 106 |Error |Fork needs 1 in and 2+ out; join needs 2+ in and 1 out
|107 / 108 |Error / Warning |Choice without outgoing transition / without guard-less else branch
|109 |Error |Junction needs incoming and outgoing transitions
|110-112 |Error |History: no parent / duplicate per region / several default transitions
|113 |Error |Direct transition between two regions of a composite (use fork/join)
|114 |Error |More than one initial state in a region of a composite
|115 |Warning |Transition between a composite and its own descendant
|116-119 |Error |Dangling parent, bad region, pseudo-state as parent, duplicate or colliding region ids
|120-123 |Error |Limits: depth 16 (and parent cycles), 16 regions, 1000 states, 256 characters per name
|124 |-- |Removed in wave 2D-a (`trigger` and `timer` combine; the number stays reserved)
|125 |Error |`after` shorter than 1 ms or longer than 3650 days
|126 |Error |Timer on a transition that leaves a pseudo-state
|127 |Warning |Two `after` timers with the same duration leave one state (only the first declared one fires)
|128 |Error |`at` instant without millisecond precision (JSON import)
|129 |Error |Guard, effect, prose, `invariant` or state action text longer than 512 characters
|130 |Warning |`showName = true` on a transition with a blank name
|131 |Error |`invariant` of a state is set but blank
|===

==== State compartment and invariant

A regular state shows its texts below the name, under a separator, in a fixed order:
`[invariant]`, `entry / ...`, `do / ...`, `exit / ...` (before wave 2D-b the order was entry, exit, do).
Blank texts give no line; the box grows with the longest line, so text never leaves the box.
`invariant` is a descriptive condition (`stateDef("Heating", invariant = "temp < 90")`); the runtime does
not evaluate it. A blank invariant is reported as rule 131. A composite state shows the same lines under its
title; the frame is at least as wide as the longest line.

Initial pseudo-states are drawn as a solid dot in the border colour of the theme. The
dot is placed 36 px in front of its target, centred on it, with a straight edge (see xref:layout.adoc[layout hints]).

Notes in a state machine wrap at 220 px, and the diagram including its notes is kept within 125 % of its width
without notes where a position allows it; otherwise notes are stacked below the diagram.

==== Timers

A transition takes a time trigger instead of an event name:

[source,kotlin]
----
import kotlin.time.Duration.Companion.seconds

transition(name = "redToGreen", source = red, target = green, timer = after(duration = 30.seconds))
transition(name = "nightMode", source = red, target = night, timer = at(iso = "2026-12-24T22:00:00Z"))
----

`after` is armed when the source state is entered and discarded when it is left; `at` is an absolute UTC instant
(ISO-8601 with `Z`, millisecond precision) that fires on the next advance if it already lies in the past. `timer` and
`trigger` combine (wave 2D-a): the transition fires on the trigger event or when the timer expires, whichever comes first, and the timer is discarded once the transition fired. The edge reads `trigger, after(30s)`; a timer alone reads `after(30s)` / `at(2026-12-24T22:00:00Z)`.

The simulator runs timers on a deterministic *virtual clock* (default start `2000-01-01T00:00:00Z`, or
`--start-time <ISO-8601 with Z>`). Time moves only through time events: `+next` jumps to the next armed timer,
`+5s`, `+250ms`, `+1m30s` advance by a duration. They are accepted in the events file of `kuml simulate`, in its
interactive mode (where `timers` lists the armed timers), by `kuml_run_event` of the MCP server and by the CLI `run`
session. The desktop simulator offers *+1 s*, *+10 s* and *Next timer*. Traces of machines with timers start with a
`ClockStarted` entry and record `TimerFired`; machines without timers keep the wall clock and their traces are unchanged.
Timers that expire at the same moment fire by deeper source first, then declaration order.

[cols="2,3"]
|===
|Limit |Value
|Armed timers per run |1024
|Timers fired by one advance |10 000
|Longest single advance (`+<duration>`) |3650 days
|Active leaf states (orthogonal regions) |64
|Junction chain length |32
|Time event string |64 characters
|===

Exceeding a limit aborts the run with an explicit message; nothing is clipped silently.

==== Guards: expressions versus prose

`guard = "vars.load < 3"` is an expression: it is parsed, type-checked and evaluated. The expression grammar accepts
`and` / `or` / `not` (case-insensitive) next to `&&` / `||` / `!`, and bracket-free identifiers in backticks for names
with spaces or umlauts (`` `Tür offen` and not alarm ``; a variable that is literally called `and` also needs backticks).
`guard = prose(text = "Antrag vollständig")` is free text: it is shown in italics, `kuml validate --strict` does not
parse it, and the simulator never evaluates it. `kuml simulate --prose-guards block` (default) treats it as false and
records `GuardNotEvaluable`; `allow` treats it as true; the desktop simulator asks with a dialog. Transition effects are
action descriptions (the simulator only logs them), so `validate` does not parse them either. An expression guard that does
not parse gets the hint to use `prose(...)` if it was meant as free text.

==== Simulation scope

The simulator runs the whole structure of a state machine:

[cols="1,3"]
|===
|Construct |Semantics
|Composite state |Entering it enters the initial state of every region; leaving it leaves all active descendants
|Orthogonal regions |A event fires at most one transition per region; an inner transition pre-empts an outer one (`Preempted` in the trace)
|Fork |Enters the target regions; regions without a target start in their initial state
|Join |Fires only when all source states are active and each leg accepts the event; otherwise `JoinWaiting` lists the missing sources
|Junction |Static chain: guards are evaluated before anything is left, then all effects run in one step; without a valid path nothing fires (`NotFired`)
|Choice |Dynamic: the branch is chosen when the choice is reached
|Shallow / deep history |Remembers the direct child / all active leaves when the composite is left; without memory the default transition, then the initial state, applies
|Final state in a region |Completes that region only; a top-level final state terminates the machine
|===

Effects of SysML 2 transitions are not executed (they are logged), as before. A transition across regions without fork or
join is rejected (code 113); the other checker errors also block simulation, naming the code.
Snapshots are written with schema version 2 (version 1 files still load as single-leaf configurations; newer versions are
rejected). Restoring a snapshot taken at an earlier scrub position in the desktop simulator does not restore history memory.

==== Limits of this version

* The LaTeX backend draws every state as a flat box and notes that in a comment.
* Regions are stacked or placed side by side by the layout engine; dashed separators follow the actual geometry.
* UML state machines (`stateDiagram`) have no DSL for orthogonal regions yet; only SysML 2 models reach the region runtime.

== Activity Diagrams (ACT)

Activity diagrams in SysML 2 model executable workflows with actions, control flow,
and parallel branches.

Rendered live below (vault source:
`03 Bereiche/kUML/Beispiele/07 SysML 2 ACT – Order Processing.md`) — swimlanes
(partitions), typed pins, a decision node, and an object flow carrying a typed order:

[source,kuml]
----
import dev.kuml.sysml2.ActionPin
import dev.kuml.sysml2.PinDirection
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "OrderProcessing") {
    partDef(name = "Customer")
    partDef(name = "OrderSystem")
    partDef(name = "Warehouse")

    val customerLane = activityPartition(name = "Customer", represents = "Customer")
    val orderSysLane = activityPartition(name = "OrderSystem", represents = "OrderSystem")
    val warehouseLane = activityPartition(name = "Warehouse", represents = "Warehouse")

    val initial = initialNode(partition = customerLane)
    val placeOrder = actionDef(
        name = "PlaceOrder",
        action = "submit(order)",
        partition = customerLane,
        pins = listOf(ActionPin(name = "orderDetails", typeId = "Order", direction = PinDirection.Output)),
    )

    val validate = actionDef(
        name = "ValidateOrder",
        action = "validate(order)",
        partition = orderSysLane,
        pins = listOf(
            ActionPin(name = "orderDetails", typeId = "Order", direction = PinDirection.Input),
            ActionPin(name = "validation", typeId = "Bool", direction = PinDirection.Output),
        ),
    )
    val decide = decisionNode(name = "valid?", partition = orderSysLane)
    val pay = actionDef(
        name = "ProcessPayment",
        action = "charge(order.total)",
        partition = orderSysLane,
        pins = listOf(ActionPin(name = "validation", typeId = "Bool", direction = PinDirection.Input)),
    )
    val cancel = actionDef(
        name = "CancelOrder",
        action = "notify(order, 'cancelled')",
        partition = orderSysLane,
        pins = listOf(ActionPin(name = "validation", typeId = "Bool", direction = PinDirection.Input)),
    )

    val reserve = actionDef(
        name = "ReserveInventory",
        action = "reserve(order.items)",
        partition = warehouseLane,
        pins = listOf(ActionPin(name = "orderDetails", typeId = "Order", direction = PinDirection.Input)),
    )
    val ship = actionDef(
        name = "ShipOrder",
        action = "dispatch(order)",
        partition = warehouseLane,
        pins = listOf(ActionPin(name = "inventory", typeId = "Inventory", direction = PinDirection.Input)),
    )
    val finalN = finalNode(partition = warehouseLane)
    val flowFinal = flowFinalNode(partition = warehouseLane)

    controlFlow(name = "start", source = initial, target = placeOrder)
    controlFlow(name = "validated", source = validate, target = decide)
    controlFlow(name = "yes", source = decide, target = pay, guard = "valid")
    controlFlow(name = "payToReserve", source = pay, target = reserve)
    controlFlow(name = "reserveToShip", source = reserve, target = ship)
    controlFlow(name = "end", source = ship, target = finalN)
    controlFlow(name = "no", source = decide, target = cancel, guard = "!valid")
    controlFlow(name = "cancelEnd", source = cancel, target = flowFinal)

    objectFlow(name = "carryOrder", source = placeOrder, target = validate, objectType = "Order")

    actDiagram(name = "Order Processing — workflow") {
        include(node = initial)
        include(node = placeOrder)
        include(node = validate)
        include(node = decide)
        include(node = pay)
        include(node = cancel)
        include(node = reserve)
        include(node = ship)
        include(node = finalN)
        include(node = flowFinal)
    }
}
----

Activity diagrams are also runnable via `kuml simulate`. The trace contains `ForkSplit`,
`JoinReached`, `ActionExecuted`, and `ActivityTerminated` entries.

NOTE: `kuml simulate` currently supports STM and ACT diagram types for SysML 2 models.
Other diagram types (BDD, IBD, REQ, SEQ, PAR) produce renderable output only.

=== Signals, regions, exceptions and pins

Besides plain actions, activity diagrams offer signal and event nodes, interruptible regions, exception
handlers and pins on any side of an action.

[cols="2,3"]
|===
| DSL | Shape

| `sendSignal("Notify", signal = "Ping")` | pentagon with the tip on the right
| `acceptEvent("Wait", signal = "Pong")` | rectangle with a notch on the left
| `acceptTimeEvent("Timeout", time = "after 10 min")` | hourglass with the time label below
| `callBehavior("Check", activityId = "StockCheck")` | action with a rake symbol; the SVG group carries `data-kuml-calls`
| `interruptibleRegion("Payment")` | dashed rounded frame around the nodes created with `region = payment`
| `exceptionHandler(protectedNode, handler, type = "IOError")` | lightning-bolt edge labelled with the type
| `controlFlow(..., interrupts = true)` | lightning-bolt edge with an open arrow
| `ActionPin(name, direction = ..., side = PinSide.Top)` | pin square on the chosen side
|===

[source,kotlin]
----
sysml2Model("Payment") {
    val payment = interruptibleRegion(name = "Payment")
    val ask = sendSignal(name = "RequestPayment", signal = "PaymentRequest", region = payment)
    val timeout = acceptTimeEvent(name = "Timeout", time = "after 10 min", region = payment)
    val cancel = actionDef(name = "CancelOrder")
    val charge = actionDef(name = "ChargeCard", pins = listOf(
        ActionPin(name = "order", direction = PinDirection.Input, side = PinSide.Top)))
    val handler = actionDef(name = "HandleError")
    controlFlow(name = "timedOut", source = timeout, target = cancel, interrupts = true)
    exceptionHandler(protectedNode = charge, handler = handler, type = "PaymentError")
    actDiagram("Payment") { include(ask); include(timeout); include(cancel); include(charge); include(handler) }
}
----

Pins: `PinSide.Auto` keeps input pins on the left and output pins on the right. An explicit side
enlarges the action box by 18 px per pin on that side. Object flows with `sourcePin` / `targetPin`
end at the pin squares: on the outer border of the square, perpendicular to the box side the pin sits on, with a
16 px stub in front of the arrowhead. The contract is checked over the whole pipeline for all four sides.

==== Structural checks (`kuml validate`, ACT)

`kuml validate` reports activity findings as `ACT301` to `ACT315`: missing signal or time expression (301/302),
overlong text (303), region cycles or nesting deeper than 4 (304), handler on itself or on a non-action (305/306),
wrong or missing pins (307), more than 8 pins per side (308), more than 8 handlers per node (309), dangling references
(310), unresolved `calledActivityId` (311), interrupting flow that does not leave a region (312), pins on pseudo
nodes (313), `showName` on non-control nodes (314) and a region spanning several partitions (315).

==== Swimlanes, regions and merges (wave 2F)

Swimlanes (`activityPartition`) are drawn as columns of equal height with a 28 px header (name semi-bold, wrapped to
the lane width). The flow runs top to bottom; a flow that returns to an earlier step (a back edge) leaves at the right
of its source and runs up in a corridor at the right of the source lane. `sameLayer(a, b)` puts the members on the
deepest layer of the group and on one centre line. Nodes without a partition stand in a header-less column at the
left. Diagrams with `direction = Right`, `Left` or `Up`, and diagrams without any partition, keep the layout of the
engine (no lane columns).

A region frame has 12 px padding; a nested region lies at least 8 px inside its parent. A node that is not a member is
pushed sideways out of the frame; if that does not succeed the warning `KUML-LAYOUT-W006` names the nodes.
`acceptEvent(name, region = r)` and `sendSignal(..., region = r)` make a signal node a member.

An interrupting flow (`controlFlow(interrupts = true)`) and an `exceptionHandler` are straight orthogonal lines with a
lightning-bolt glyph where the line leaves the region of its source; the flow name (and guard) is its label. An object
flow shows its type as `«Type»`. Names of signal, accept-event and time-event nodes are wrapped (at most four lines,
then the node grows wider) and never shortened. Several arrivals at a decision or merge diamond are spread along its top
side; from five arrivals on the diamond grows.

==== Limits

A node that the layout places inside a region frame in a diagram without partitions, or in a diagram flowing sideways,
looks like a member although it is not (the pushing out of the frame exists only for lane columns). The simulation
passes tokens through the new node kinds; regions, interruptions and handlers have no runtime semantics yet.

Time-ordered interaction between blocks: lifelines, messages, execution

=== Nested fragments, `ref`, time constraints, found and lost messages

Combined fragments can be nested with the block form; every nested fragment is registered with
its parent operand. Fragments nested deeper than 8 levels (or with unknown or cyclic parents) are
rendered flat, never rejected by the renderer; `kuml validate` reports them.

[source,kotlin]
----
combinedFragment("retry", CombinedFragmentOperator.Loop) {
    operand(guard = "attempts < 3", start = 1, end = 5) {
        combinedFragment("cache", CombinedFragmentOperator.Alt) {
            operand(guard = "hit", start = 1, end = 2)
            operand(guard = "miss", start = 3, end = 4)
        }
    }
}
interactionUse(name = "auth", refersTo = "Authenticate", lifelines = listOf(user, browser), seqNo = 8)
durationConstraint(lifeline = user, from = 0, to = 2, expression = "0..3s")
timeObservation(lifeline = browser, seqNo = 0, name = "t0")
foundMessage(label = "ping", target = browser, seqNo = 9)
lostMessage(label = "drop", source = browser, seqNo = 10)
----

* A nested frame is inset by 10 px per level on both sides and starts one header band below its parent.
* `interactionUse` (`ref`) draws a 48 px high frame from the leftmost to the rightmost covered lifeline
  (+16 px); the referenced name is plain text, never a link. Following rows move down by 16 px.
* `durationConstraint` draws a bracket 14 px right of the lifeline axis (of the activation bar if present);
  `timeObservation` draws a tick labelled `name = now`. Lifeline spacing grows so the texts do not run
  into the neighbouring lifeline.
* Found and lost messages are 80 px long with a filled 5 px circle; the lifeline order of a diagram is
  always the declaration order.
* The `«destroy»` label keeps clear of the 16 px X marker.

Not supported in this version: interaction gates, nested fragments and the new constructs in the LaTeX
output (the LaTeX SEQ renderer keeps its rectangle fallback and draws no fragments at all).

| `SEQ402` | Error | unknown parent, self reference or cycle

=== Fragments, time and found messages (wave 2F)

A combined fragment is as wide as the lifelines it covers: the lifelines of the messages, `ref` frames, time
observations and duration constraints in its rows and of its nested fragments, plus 24 px. It ends below its last
content (a self loop, a `ref` frame) and keeps at least 12 px from the next fragment. An operand without a guard
(`guard = ""` or none) writes no text; its divider remains, which is the usual form for `par`.

[source,kotlin]
----
foundMessage(label = "open", target = vitec, seqNo = 0, source = person)   // arrow from the sending lifeline, dot at its start
timeObservation(lifeline = fmcs, seqNo = 3, name = "tOpen", label = "now") // shown as `tOpen = now`; without label only `tOpen`
----

A `ref` frame is as high as its text plus 12 px (at least 28 px). A self message is a 32 x 20 px loop with its label
on the right. A duration constraint stands 12 px left of the outermost activation bar. Found and lost lines are at
least 120 px long, the label stands above the line. The lifelines start 24 px below the top of the image and end 24 px
above its bottom.

=== Nested constraints and pins

Every constraint parameter is drawn as a small square _pin_ on the box frame: `in` parameters on the
left, `out` and `inout` on the right, at the height of the parameter's row. A binding whose endpoint is
`"<constraint>::<parameter>"` ends at that pin. The helper `constraint.pin("name")` builds the endpoint id
and fails while the model is built if the constraint has no such parameter. An endpoint that names a
constraint but no existing parameter ends at the box centre and `kuml validate` warns (`PAR441`).
A binding ends on the border of the pin square, perpendicular to the frame: on the outer face for a binding that
comes from outside the constraint, on the inner face for a binding that runs inside it.

A constraint can be nested in another one with `parent = outer`. The inner box is drawn inside the outer
box; bindings between the outer pins and the inner pins, and between inner constraints, run inside the outer
box and carry no label. Two levels are recommended; the hard limit is four levels (the outer constraint counts
as level one) and 64 parameters per constraint.

Rendered live below (vault source: `03 Bereiche/kUML/Beispiele/51 SysML 2 PAR – Verschachtelte Constraints.md`):

[source,kuml]
----
import dev.kuml.sysml2.ConstraintParameter
import dev.kuml.sysml2.ConstraintParameterDirection.In
import dev.kuml.sysml2.ConstraintParameterDirection.Out
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "VehicleDynamicsModel") {
    attributeDef(name = "Mass")
    attributeDef(name = "Force")
    attributeDef(name = "Speed")
    attributeDef(name = "Acceleration")

    val dynamics = constraintDef(
        name = "VehicleDynamics",
        expression = "a = (F_drive - k * v^2) / m",
        parameters = listOf(
            ConstraintParameter(name = "m", typeId = "Mass", direction = In),
            ConstraintParameter(name = "F_drive", typeId = "Force", direction = In),
            ConstraintParameter(name = "v", typeId = "Speed", direction = In),
            ConstraintParameter(name = "a", typeId = "Acceleration", direction = Out),
        ),
    )
    val drag = constraintDef(
        name = "Drag",
        expression = "F_net = F_drive - k * v^2",
        parameters = listOf(
            ConstraintParameter(name = "F_drive", typeId = "Force", direction = In),
            ConstraintParameter(name = "v", typeId = "Speed", direction = In),
            ConstraintParameter(name = "F_net", typeId = "Force", direction = Out),
        ),
        parent = dynamics,
    )
    val newton = constraintDef(
        name = "NewtonsLaw",
        expression = "a = F / m",
        parameters = listOf(
            ConstraintParameter(name = "F", typeId = "Force", direction = In),
            ConstraintParameter(name = "m", typeId = "Mass", direction = In),
            ConstraintParameter(name = "a", typeId = "Acceleration", direction = Out),
        ),
        parent = dynamics,
    )
    val vehicle = partDef(name = "Vehicle") {
        attribute(name = "mass", typeId = "Mass")
        attribute(name = "driveForce", typeId = "Force")
        attribute(name = "speed", typeId = "Speed")
        attribute(name = "acceleration", typeId = "Acceleration")
    }

    // Vehicle attributes to the pins of the outer constraint
    bind(name = "mass_to_m", source = "Vehicle::mass", target = dynamics.pin("m"))
    bind(name = "drive_to_F", source = "Vehicle::driveForce", target = dynamics.pin("F_drive"))
    bind(name = "speed_to_v", source = "Vehicle::speed", target = dynamics.pin("v"))
    bind(name = "a_to_accel", source = dynamics.pin("a"), target = "Vehicle::acceleration")
    // Outer pins to inner pins
    bind(name = "F_to_drag", source = dynamics.pin("F_drive"), target = drag.pin("F_drive"))
    bind(name = "v_to_drag", source = dynamics.pin("v"), target = drag.pin("v"))
    bind(name = "m_to_newton", source = dynamics.pin("m"), target = newton.pin("m"))
    // Between the inner constraints
    bind(name = "net_to_newton", source = drag.pin("F_net"), target = newton.pin("F"))
    // Inner pin back to the outer pin
    bind(name = "newton_to_a", source = newton.pin("a"), target = dynamics.pin("a"))

        include(definition = dynamics)
        include(definition = drag)
        include(definition = newton)
        include(definition = vehicle)
    }

=== Rows, expressions, units and binding labels

* Parameter rows are 18 px apart, so the pin squares (8 px) of one box never touch. Box text and pins share one
  geometry.
* An expression wraps at 60 characters per line, preferably before `&&` or `||`, then before a comparison operator
  or `+`/`-`, then at a blank (a single token longer than 60 characters is cut hard). The box grows with the line
  count. An expression is capped at 200 characters (then `...`); longer text is a model smell, not a rendering task.
* A parameter row shows the unit of its type: with `attributeDef(name = "Druck", unitSymbol = "Pa")` a parameter
  `typeId = "Druck"` reads `«in» pMix : Druck [Pa]`. A unit is only shown through the parameter type; including
  the `attributeDef` in the diagram does nothing (`PAR442`).
* Binding labels stand beside their line with at least 2 px to every line, line end, box, pin and other label. If
  no spot is free the label is drawn on its line and `kuml render` reports `KUML-LAYOUT-W005`.

Known limits: a binding that crosses more than one nesting level (outer pin to a grandchild pin) is drawn as a
straight line between the two pins, and the LaTeX renderer still draws constraint boxes without pins.

== Package diagrams (wave 2I-a)

A package diagram shows how a model is organised: packages as nested frames, the definitions they own as cards,
`import` relationships as dashed arrows, and views and viewpoints as cards. Kotlin reserves `package` and `import`, so
the DSL words are `pkg` and `imports`.

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "PlatformStructure") {
    pkg("Common") {
        attributeDef("Mass", id = "Common::Mass")
        portDef("PowerPort", id = "Common::PowerPort")
    }
    pkg("Vehicle") {
        imports("Common::*")                        // the direct members
        imports("Common::PowerPort", public = true) // one member, re-exported
        partDef("Vehicle", id = "Vehicle::Vehicle")
        pkg("Drive") {
            imports("Common::**")                   // the namespace and everything nested in it
            partDef("Motor", id = "Vehicle::Drive::Motor")
        }
    }
    val safety = viewpoint("Safety") {
        stakeholder("Safety engineer")
        concern("Hazards are covered")
    }
    val overview = view("Safety Overview") {
        satisfies(safety)
        expose("Vehicle::*")
        filter("@Safety")
    }
    packageDiagram(name = "Platform") {
        includeById("pkg:Vehicle")
        includeById("pkg:Common")
        include(overview)
        include(safety)
    }
}
----

* `pkg(name) { ... }` declares a package; every definition registered inside the block belongs to it. Packages nest
  (up to 8 levels). The package id is `pkg:<qualifiedName>` (`pkg:Vehicle::Drive`). Names must not contain `::`.
* A definition keeps its id; its qualified name is derived from its package (`Vehicle::Drive::Motor`). Two definitions with
  the same name in different packages need an explicit `id = "..."` each.
* `imports("P::*")` imports the direct members of `P`, `imports("P::**")` the whole sub-tree, `imports("P::X")` one
  member. `public = true` marks a re-exporting import; the default is private. `imports` is only allowed inside a
  `pkg` block.
* `viewpoint(name) { stakeholder(..); concern(..) }` and `view(name) { satisfies(..); expose(..); filter(..) }`. Ids
  are `viewpoint:<name>` and `view:<name>`. `satisfies` takes a handle or a name.
* `packageDiagram(name) { include(...) }` takes packages (with their sub-tree and members), definitions (a card; on root
  level when their package is not drawn), views and viewpoints. `includeById("pkg:Vehicle")` is the id form.

=== What is drawn

* Packages are **unfilled** frames (1 px) with a name tab at the top left. Three levels are frames; a package from the
  fourth level on is a flat card inside the level-3 frame: its tab reads `C::D` or `C::D::E` (relative to the level-3
  package), below it the names of its members (11 px, at most 8, then `+N more`).
* An import is a dashed arrow (`6 4`) with an open head from the importing package to the target. The label is
  `«import»`, `«import» *` or `«import» **`, with `public ` in front for a public import. The target is the frame of a
  package (`*`, `**`) or the card of a member.
* An import that cannot be an arrow is an italic text line `import X::*` under the tab of its frame: the target is
  not drawn or unknown, or it is the own package, an ancestor or a descendant.
* A view or viewpoint is a card with the keyword `«view»` or `«viewpoint»`, the name, and the fields `expose` and `filter`
  (view) or `stakeholders` and `concerns` (viewpoint); empty fields are left out. A view points at each of its viewpoints
  with a dashed `«satisfy»` arrow.
* `layout { }` works as on the other layered diagrams. Notes can be anchored to definition cards.

=== Package findings

`kuml validate` reports `KUML-PKG-E001` (package cycle or unknown parent), `KUML-PKG-E002` (a view satisfies an unknown
viewpoint), `KUML-PKG-E003` (limit exceeded: 128 packages, 8 levels, 256 imports, 128 views, 32 entries per view),
`KUML-PKG-W001` (import target unknown), `KUML-PKG-W002` (a package lists an unknown member), `KUML-PKG-W003` (the
diagram lists an unknown id), `KUML-PKG-W004` (import of the own package, an ancestor or a descendant), and
`KUML-PKG-W005` (a package nested deeper than three levels in the diagram; it is drawn as a card).

=== Known limits

* **Views are not evaluated.** `expose` and `filter` are text on the view card; they do not change what a diagram
  draws (ADR-0016, option 3, is wave 2I-b).
* Stakeholders and concerns are text, not model elements.
* There is no LaTeX rendering: `kuml render --format latex` stops with "Package diagrams are not supported by the LaTeX
  renderer yet (wave 2I-a)".
* BDD and IBD do not draw package frames.
* The knowledge-workspace export (`kuml convert`) has no standard OKF type for package diagrams yet.

== Analysis cases, calculations, perform and exhibit (wave 2I-b)

Wave 2I-b adds two definition kinds and two block compartments to the block definition diagram (BDD). They are drawn
as block-like boxes; no new diagram kind exists.

* `calcDef("TotalMass") { input("a", "Mass"); expression("a + b"); returns("total", "Mass") }` is a calculation. The box is
  `<<calc def>>` with the compartments `parameters` (`in a : Mass`, `out ...`, `inout ...`), `expression` (monospaced and
  wrapped at 34 characters) and `return`.
* `analysisDef("MassAnalysis") { subject(vehicle); objective("..."); calc("total", totalMass); returns("ok", "Boolean") }` is
  an analysis case. The box is `<<analysis def>>` with the compartments `objective` and `return`. Each `calc` is a
  composition (filled diamond at the analysis) to its calculation, labelled with the name of the calc; the `subject` is a
  dashed arrow with `<<subject>>` to the analysed definition.
* On a block: `perform("drive", driveAction)` and `exhibit("charging", chargingState)` add the compartments
  `perform actions` and `exhibit states` with the lines `perform drive : Drive` and `exhibit charging : Charging`, in
  declaration order. Both are lines, not edges.

[source,kuml]
----
import dev.kuml.sysml2.dsl.sysml2Model

sysml2Model(name = "MassAnalysis") {
    val mass = attributeDef("Mass", unitSymbol = "kg")
    val vehicle = partDef("Vehicle") { attribute("curbMass", mass.id) }
    val total = calcDef("TotalMass") {
        input("chassis", "Mass")
        input("battery", "Mass")
        expression("chassis + battery")
        returns("total", "Mass")
    }
    val analysis = analysisDef("MassAnalysis") {
        subject(vehicle)
        objective("Stay below the permitted gross mass.")
        calc("total", total)
    }
    bdd("Mass analysis") {
        include(analysis)
        include(total)
        include(vehicle)
    }
}
----

The object overloads (`calc("total", totalMass)`, `perform("drive", driveAction)`) need the target to be declared first.
For a forward reference or a cycle use the id overload: `calc("total", "TotalMass")`, `perform("drive", "Drive")`,
`subject("Vehicle")`.

A calc whose calculation is not in the diagram, and a subject that is not in the diagram, stay as lines in the box
(`calcs`, `subject`) instead of an arrow, so the information is never lost. Type names of parameters are free text and
are not resolved.

=== Findings

`kuml validate` reports these errors for a BDD (the codes are stable):

| Code | Meaning

| `SYSML2_CALC_REF_UNKNOWN` | a calc points at nothing, or at a definition that is not a calculation
| `SYSML2_ANALYSIS_SUBJECT_UNKNOWN` | the subject of an analysis does not exist
| `SYSML2_PERFORM_TARGET_NOT_ACTION` | a perform points at nothing, or at a definition that is not an action
| `SYSML2_EXHIBIT_TARGET_NOT_STATE` | an exhibit points at nothing, or at a definition that is not a state

=== Known limits

* A compartment shows at most 20 lines; longer lists and texts end with an ellipsis (the model keeps everything).
* No separate analysis view, no analysis or calc usages as model elements of their own, no calc in parametric or
  internal block diagrams, no edge for `exhibit` and `perform`.
* The LaTeX renderer draws an analysis or a calculation as a plain labelled rectangle without compartments.

== Notes

Note text may use bold, italic, code, links and lists, see xref:uml-dsl.adoc#formatted-note-text[Formatted note text].

SysML 2 models carry free-text comments. Use `comment(...)` (alias `note(...)`) either on the model or
inside a diagram block:

[source,kotlin]
----
sysml2Model(name = "Vehicle") {
    val vehicle = partDef(name = "Vehicle")
    val engine = partDef(name = "Engine")

    // model level: shown in every diagram in which one of its anchors is visible
    comment(text = "Engine and vehicle are developed by different teams.", vehicle, engine)

    bdd(name = "Overview") {
        include(definition = vehicle)
        include(definition = engine)
        // diagram level: stored in the model and listed in this diagram
        comment(text = "Free-standing note", id = "legend")
    }
}
----

* Anchors are element ids (`comment(text = "...", "Vehicle", "Engine")`) or element handles
  (`comment(text = "...", firstAnchor = vehicle)`). Without anchors the note is free-standing.
* A comment appears in a diagram if its id is listed in the diagram's `noteIds` (via a comment inside the
  diagram block, `include(comment)` or `includeCommentById(id)`), or if at least one anchor is visible there.
  Links to invisible targets are not drawn. Note ids never go into `elementIds`, because an empty
  `elementIds` means "show everything" for some diagram kinds.
* Notes are placed after the layout, close to their anchors, away from nodes, labels, composite titles and
  other notes. Every anchor gets its own dotted line with a dot at the anchor end; free-standing notes form
  a grid (at most four columns) right of the diagram.
* Anchorable: definitions and usages that the diagram draws, and also transitions (STM), connections and
  part ports (IBD, `comment(text, "Battery::dcOut")`), the owner of an IBD, activity partitions (ACT), nested
  constraints (PAR) and lifelines (SEQ). In a sequence diagram the line ends on the lifeline stem; for an
  inner lifeline it may have to cross another lifeline when no free column exists.
* Body limit: 65 536 characters (hard), display limit 2000 characters / 30 lines; at most 8 anchors per
  note and 200 notes per diagram are drawn (`KUML-NOTE-W003`).
* A note whose anchor id does not exist is drawn free-standing and reported as `KUML-NOTE-W001`
  (`Anker unbekannt: <id> (Notiz <noteId>)`); an anchor the diagram kind cannot draw is `KUML-NOTE-W002`.
  `kuml validate`, `kuml render`, `kuml workspace validate --evaluate`, Desktop validate and render report
  them with the ids, never with the note text. `SYSML2_NOTE_ANCHOR_UNKNOWN` and `SYSML2_NOTE_DUPLICATE_ID`
  (errors) and `SYSML2_NOTE_NOT_SHOWN` (warning) remain.

NOTE: The LaTeX/TikZ export draws notes (kinds, formatted text, anchor lines). A note anchored only to a port, an owner frame, a partition or a nested constraint has no anchor geometry there and is left out.

== Ports, flows and allocations

[source,kotlin]
----
portDef("FuelPort") { flowProperty("fuel", "Fuel", PortDirection.In) }
partDef("Engine") { port("injector", "FuelPort", direction = PortDirection.In, conjugated = true) }
partDef("Vehicle") {
    port("fuelIn", "FuelPort", direction = PortDirection.In)
    part("engine", "Engine")
    refPart("tank", "Tank")
    connect("feed", "FuelLine", "tank.outlet", "engine.injector")
    flow("Fuel", "tank.outlet", "engine.injector", via = "feed")
}
allocate("Controller", "Vehicle")
----

Dotted paths exist only in the DSL; the model stores `Owner::part::port`. A conjugated port inverts
`in` and `out` of its flow properties (`effectiveDirection`); the drawn triangle shows the declared
direction, the conjugation is visible as `~Type` in the label.

== IBD frame

An IBD draws an owner frame with boundary ports only when a connection, flow or binding ends on a port
of the owner, or reaches deeper than one path step below a visible part. Otherwise it renders without
a frame.

Parts nested inside a visible part are drawn box in box, recursively (depth limit 8, at most 256 paths). The visible
part box is level 1 and keeps its two-line head (`<<part>>` and `name : Type`); every nested part is a frame inside
its parent with a single header line of 22 px (`name : Type`). A frame keeps 16 px inner distance to the frames
inside it on the left, right and bottom and a little more below its header, so port labels fit. The fill alternates by
level: odd levels use the part colour, even levels the canvas colour. The attribute compartment (`showAttributes`) sits
below the header of every part that has attributes. A port sits on the border of the frame of its own part. A connector
that ends on a nested port is routed to a gate on the border of the visible part box and then runs straight into the
frame; it crosses only the frames around its target, never another part. The gate and the port move along the frame (or
to another side) until the straight way crosses no title, attribute text or foreign frame.

== BDD relationships

Compositions (filled diamond), aggregations (`refPart`, hollow diamond), associations (a connection
definition with two block-typed parts, not itself shown) and allocations are drawn as edges when both
ends are visible; the matching rows leave the feature compartment. Blocks show `actions` and
`flows` compartments (`<dir> <name> : <Type>` per flow property of their ports) when non-empty; attribute definitions with a unit show `unit = <symbol>`.

== Use-case and block definition diagrams (wave 2E-b)

=== Use-case diagrams

* A use case that is only listed inside a `subject { include(...) }` block is a member of the diagram. Until wave 2E-b
  it was dropped silently, together with every association, `include` and `extend` that touched it. Check 219 warns when
  such a line still points at an element that is not shown.
* `extend(source, target, condition = "...", extensionPoint = "...")`: the line carries `<<extend>>` and, below it,
  `[condition]` (wrapped at 28 characters, at most three lines, longer text is cut with an ellipsis; check 220 hints).
  The extension point is drawn inside the extended use case (the target): a divider, the heading `extension points` and
  one line per point (at most six, 40 characters each). The ellipse grows with the block.
* `layout { actorSide = ActorSide.Auto | Left | Right | Both }` and the grid layout: see the layout chapter.
* Edge labels of use-case diagrams are placed by the label placer (like the BDD), so a label avoids nodes and lines.

=== Block definition diagrams

* **Attribute defaults:** `attribute("pressure", pressureType.id, default = -5.0)` stores the plain number; the unit comes
  from the attribute definition (`attributeDef("Pressure", unitSymbol = "Pa")`), so it is written once. The block shows
  `pressure : Pressure = -5 Pa` (integral numbers without `.0`, a non-breaking space before the unit, `.` as decimal
  separator whatever the locale). The older `default = 1500.kg` form shows as `1500 kg` too. `kuml validate` reports a
  default whose unit differs from the type's unit (501) and an enumeration default that is not a literal (502, 503).
  New unit constants and literals: `Unit.PASCAL` (`5.Pa`), `Unit.CELSIUS` (`21.degC`, symbol `°C`), `Unit.MILLIAMPERE`
  (`4.mA`); any other symbol works with `attributeDef(unitSymbol = "bar")`.
* **Enumerations:** `enumerationDef("Colour") { literal("Red"); literal("Green") }` is drawn as `<<enumeration>>` with one
  literal compartment (at most 64 literals); `attribute("colour", colour.id, defaultLiteral = "Red")` shows
  `colour : Colour = Red`.
* **Action definitions** in a BDD are blocks with `<<action def>>`. An `allocate` edge docks at the line of the
  allocated action in the `actions` compartment of the target block when the flow is `Right` or `Left`.
* **Roles and multiplicities:** the role name of a composition or reference is a label in the middle of the line (placed
  by the label placer, never stacked at the target); the multiplicity (`1` is not drawn) stays at the target end.
* **`refPart`** is a reference: a plain line with an open arrow at the referenced block, no diamond. (Until now it was
  drawn as an open diamond, which UML reserves for shared aggregation.)
* **Generalisation:** a block with three or more specialisations that has no other edge is placed centred above (flow
  `Up`: below) them. The edges form a bus: one hollow triangle, a trunk and a horizontal bus; specialisations of a second
  row reach the bus through the gaps between the columns above. `wrapColumns` sets the number of specialisations per row.
* **Box size** grows with the number of edges at a block (14 px per edge beyond two, at most 112 px, across the flow).
